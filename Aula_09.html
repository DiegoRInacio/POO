Mudança de mentalidade

O Mito do “Funciona na Minha Máquina”

A ambiguidade humana
Sem testes automatizados, o comportamento depende da perspectiva de quem executa. O que parece correto para o desenvolvedor pode falhar para o usuário.
A certeza executável
Testes substituem confiança cega por evidências lógicas, repetíveis e executáveis.
Um teste útil responde automaticamente: dada esta situação, quando esta ação ocorre, o resultado esperado aparece?
Conceito

Verificação × Validação

Verificação
Estamos construindo o produto corretamente?

Confere se o código respeita projeto, sintaxe, contratos e lógica da POO.
Validação
Estamos construindo o produto certo?

Confere se o software atende aos requisitos do usuário e resolve o problema real.

Qualidade exige as duas perguntas: código impecável para o requisito errado também é falha.

Estratégia

A Pirâmide de Testes

E2E / UI
Lentos e caros; simulam o usuário de ponta a ponta.
Integração
Verificam a comunicação entre componentes e serviços.
Unitários · foco do laboratório
Rápidos, baratos e isolados; testam métodos e classes.
Em POO, garantir a integridade de um objeto isolado é o primeiro passo para um sistema robusto.
Anatomia de um teste

O Padrão AAA

1. Arrange · PrepararInstanciar objetos e configurar o estado inicial. Ex.: criar uma conta com saldo de R$ 100.
2. Act · AgirExecutar apenas o comportamento testado. Ex.: chamar depositar(50).
3. Assert · VerificarComparar o resultado real com o esperado. Ex.: saldo igual a R$ 150.

Separar as três fases deixa o teste legível e torna a causa de uma falha mais fácil de localizar.

Test-Driven Development

TDD: o Teste como Guia

1. Red · Falhar
Escreva um teste para um comportamento que ainda não existe. Ele deve falhar.
2. Green · Passar
Implemente o código mais simples que faça o teste passar.
3. Refactor · Refatorar
Melhore a estrutura sem alterar o comportamento protegido pelo teste.
O ciclo é curto e se repete: falha → passa → melhora. O teste orienta o design e protege a refatoração.
Lógica universal

Sintaxes Diferentes, Mesma Arquitetura

POO e testes unitários transcendem a linguagem. O engenheiro adapta a ferramenta, mantendo intenção, isolamento e padrão AAA.

Python
Biblioteca padrão unittest; classes de teste herdam de unittest.TestCase.
JavaScript
Framework Jest; suítes usam blocos describe e casos usam test.
Cenário prático

A Classe que Será Testada

Vamos testar um objeto simples: uma Calculadora.

O objetivo é garantir que o método somar processe corretamente dois parâmetros.

Calculadora

+ somar(a: float, b: float): float
Caso esperado: somar(2, 3) deve produzir 5.
Matriz comparativa

Configurando o Ambiente de Teste

Python · unittest
import unittest
from calculadora import Calculadora

class TestCalculadora(unittest.TestCase):
    # herda as asserções do framework
    pass
JavaScript · Jest
const Calculadora = require('./calculadora');

describe('Calculadora', () => {
  // a suíte agrupa os casos de teste
});

Python usa herança; Jest organiza o ambiente com funções e closures.

Matriz comparativa

Executando o Padrão AAA

Python · unittest
def test_somar_dois_numeros(self):
    calc = Calculadora()           # Arrange
    resultado = calc.somar(2, 3)  # Act
    self.assertEqual(resultado, 5) # Assert
JavaScript · Jest
test('deve somar dois números', () => {
  const calc = new Calculadora();     // Arrange
  const resultado = calc.somar(2, 3); // Act
  expect(resultado).toBe(5);          // Assert
});
A asserção muda — assertEqual × expect().toBe() —, mas a arquitetura lógica é a mesma.
Valor de engenharia

O Teste como Documentação Viva

Segurança na refatoração
Alterações futuras não devem quebrar funcionalidades existentes: testes detectam regressões.
Design superior
Código difícil de testar costuma revelar alto acoplamento. Testabilidade favorece encapsulamento e responsabilidades claras.
Verdade executável
Comentários envelhecem; um teste prova continuamente o comportamento atual da classe.
Checkpoint

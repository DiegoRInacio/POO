O Paradigma da Comunicação

Já vimos abstração, herança (via classes abstratas) e o vocabulário de composição/agregação. Hoje: Interfaces — o contrato que faz módulos diferentes conversarem sem se conhecer por dentro.

Sem interface (o caos)
Módulos interpretam dados e ações de forma conflitante — cada um "fala" uma língua diferente. O resultado é a quebra do sistema.
Com interface (o contrato)
Uma interface garante o "o quê" deve ser feito, ignorando o "como" funciona por dentro — como um encaixe USB: não importa o que tem dentro do cabo.
Conceito 1

Assinaturas de Método e o Contrato Explícito

Regra de ouro: a classe que assina o contrato (implementa a interface) é obrigada a fornecer o corpo e a lógica daquele método. A assinatura define só o nome, os parâmetros e o retorno.

classDiagram class Imprimivel { <<interface>> +imprimir()* } class Relatorio { +imprimir() } class Fatura { +imprimir() } Relatorio ..|> Imprimivel Fatura ..|> Imprimivel

Seta tracejada + triângulo vazado = realização (implementa a interface)

Python

O Contrato em Python (módulo abc)

A mesma mecânica de ABC/@abstractmethod da Aula 05 — só que aqui a classe não tem nenhum método implementado, só contratos. Isso é o que separa uma interface de uma classe abstrata comum.

from abc import ABC, abstractmethod

class Imprimivel(ABC):
    @abstractmethod
    def imprimir(self):
        pass

class Relatorio(Imprimivel):
    def imprimir(self):
        print("Gerando relatório...")
JavaScript

Simulando o Contrato em JavaScript

JS não tem a palavra-chave interface em tempo de execução. A solução é estrutural: uma classe "escudo" lança erro se o método não for sobrescrito.

class Imprimivel {
  imprimir() {
    throw new Error("O método imprimir() deve ser implementado.");
  }
}

class Relatorio extends Imprimivel {
  imprimir() {
    console.log("Gerando relatório...");
  }
}
Conceito 2

Polimorfismo Direcionado por Interfaces

O cliente não precisa saber qual é a classe concreta. O polimorfismo real acontece quando o sistema itera com múltiplos objetos diferentes, confiando apenas numa assinatura em comum.

Python 
def processar_lote(documentos):
    for doc in documentos:
        doc.imprimir()

fila = [Relatorio(), Fatura(), Relatorio()]
processar_lote(fila)
JavaScript 
const fila = [
  new Relatorio(), new Fatura(), new Relatorio()
];
fila.forEach(doc => doc.imprimir());
Insight arquitetônico: processar_lote está blindada. Podemos criar 100 novas classes amanhã — desde que assinem o contrato Imprimivel, esse loop jamais precisa ser reescrito.
Conceito 3

Duck Typing: a Interface Implícita

"Se anda como um pato e grasna como um pato…" — linguagens dinâmicas aceitam interfaces baseadas no comportamento real, não em declarações nominais de herança. A verificação do contrato acontece no momento do uso.

Python — confia no comportamento 
obj.grasnar()
# o Python não liga pra árvore
# genealógica do objeto
JavaScript — checagem defensiva 
function acionarPato(obj) {
  if (typeof obj.grasnar === "function") {
    obj.grasnar();
  } else {
    console.warn("Contrato violado.");
  }
}
Conceito 4 · o "I" do SOLID

Princípio da Segregação de Interfaces

O problema — interface gorda
IEquipamento com imprimir(), escanear(), enviarFax() — uma ImpressoraBasica é forçada a depender de métodos que nunca vai usar.
A solução — segregação
Três interfaces pequenas: Imprimivel, Escaneavel, Fax. A ImpressoraBasica implementa só Imprimivel.
Nenhum cliente deve ser forçado a depender de métodos que ele não utiliza.
Refatorando para coesão

Composição de Interfaces

Interfaces pequenas e coesas agem como blocos de montar — permitem compor comportamentos com precisão cirúrgica.

Python — múltiplas ABCs 
class Multifuncional(Imprimivel, Escaneavel):
    def imprimir(self): ...
    def escanear(self): ...
JavaScript — mixins 
const Multifuncional = Object.assign(
  {}, ComportamentoImprimir, ComportamentoEscanear
);
